# Hermes runs across devices

[Onyx issue #2](https://github.com/RafyTime/onyx/issues/2) asks whether a private Onyx client can start work in Hermes, leave, and recover the result and history elsewhere. Hermes Agent v0.23.3 provides the pieces for that flow on the same gateway and profile. Use the Runs API for execution and the Sessions API for the transcript. Share the Onyx-to-Hermes IDs through Onyx's backend so the second device can recover them without access to the first device's storage. This finding comes from release documentation, source, and upstream test inspection. The two-device flow still needs a live test. [Hermes release][release] · [Runs API][runs] · [Sessions API][sessions]

## API choices

| Interface | Fit for Onyx |
| --- | --- |
| `POST /v1/runs` and `GET /v1/runs/{run_id}` | Submit one turn and receive a run ID with HTTP 202. The gateway schedules execution independently of the request. Poll for state and final `output`. Subscribe separately to `/events` for progress. [Runs API][runs] · [Run launch source][launch] |
| `/api/sessions` and `GET /api/sessions/{id}/messages` | Create or list sessions and read their stored transcripts. The synchronous `/chat` runs a turn in the request. The `/chat/stream` handler explicitly interrupts its turn on a detected disconnect or cancellation. [Sessions API][sessions] · [Disconnect handler][disconnect] |
| `/v1/chat/completions` and `/v1/responses` | Compatibility interfaces for request-bound turns. Chat Completions can continue an API session with `X-Hermes-Session-Id`. Responses supports stored results by response ID and continuation via `previous_response_id` or a named conversation. Stored response snapshots survive restart subject to LRU eviction. Runs provides the explicit submit-and-poll contract for this task. [Chat Completions][chat] · [Responses][responses] · [Storage limits][limits] |
| Gateway WebSocket JSON-RPC | Use this if Onyx needs to attach to a session owned by another Hermes surface. The shared gateway supports `prompt.submit` and `session.resume`, whose `inflight` snapshot can rebuild the active turn UI. This requires the gateway's ticket and session protocol. ACP is primarily an IDE integration over stdio. The Jobs API manages scheduled work. [Programmatic integration][integration] · [Jobs API][jobs] |

## Identity and recovery

1. Confirm the deployed API with `GET /v1/capabilities`. Look for run submission, polling, session history and durable Runs idempotency. Use the same Hermes gateway, profile and credential scope across devices. Keep the bearer key on the Onyx backend and authenticate devices to Onyx. Run ownership is scoped by profile and credential. Treat the IDs as references to authorized records. [Capabilities][capabilities] · [Capability implementation][cap-source] · [Authentication][auth] · [Run ownership source][owners]
2. Keep an Onyx conversation ID mapped to an API-owned Hermes `session_id`. Onyx can call `POST /api/sessions` and store the returned ID, or supply a stable ID that Hermes is allowed to create. Hermes rejects an attempt to take over a CLI, TUI, Desktop, ACP or messaging session through these API routes. For a follow-up send the session ID and omit explicit history and `previous_response_id` so Hermes loads the current transcript. Context compaction can rotate the live session ID. Runs and transcript reads resolve the live continuation, and the transcript response reports its resolved ID. [Run submission][runs] · [Session creation source][create] · [Run session resolution][session-resolution] · [Transcript source][transcript]
3. Persist a separate Onyx submission record with the request body and a unique `Idempotency-Key` before dispatch. Save the returned Hermes `run_id` against that record. The run ID identifies one execution. The session ID identifies its conversation. A Responses `response_id` identifies a stored response, and `X-Hermes-Session-Key` is a separate conversation and memory-scoping input. An exact Runs retry under the original scope and key returns the original run ID. Changed JSON under the same key returns `409 idempotency_key_conflict`. The ordinary keyed replay window is 24 hours after the last status update. Respect `Retry-After` on transient admission failures. Once replay is uncertain, reconcile the original submission before considering any new dispatch. [Run submission][runs] · [Key storage][ledger] · [Session key][session-key]
4. Device B loads the shared Onyx submission and polls `GET /v1/runs/{run_id}`. If the submit reply was lost, Onyx can recover the ID with the original keyed request within its replay window. Read the transcript separately with `GET /api/sessions/{id}/messages`, using `include_compacted=true` and paging when older turns matter. Keep the final run result and status in Onyx if per-run lookup must outlast Hermes retention. A transcript can show what was said without proving the outcome of a specific admission. The adapter has a short-lived in-memory status cache, a durable keyed ledger and, for canonical runs, a projection from the admission store. Treat these as bounded recovery paths. [Run polling][status] · [Durable status source][durable] · [Admission projection][projection] · [Transcript source][transcript]

## Disconnect and interruption

- Disconnecting from run events detaches the subscriber. The execution task is separate. Resume with `Last-Event-ID` or `?last_seq=` and deduplicate by sequence. v0.23.3 keeps a 1,000-event in-memory backlog. The sweeper may drop unsubscribed buffers about five minutes after creation, even while work continues. A reconnect can receive `replay.truncated` or a missing stream. Use polling and history to rebuild the view. Upstream tests cover two subscribers, disconnect and replay of missed events. [Run event buffer][buffer] · [Event handler][events] · [Transport sweeper][sweeper] · [Retention constants][ttl] · [Upstream tests][tests]
- Explicit stop is asynchronous. `POST /v1/runs/{run_id}/stop` asks Hermes to interrupt and returns `stopping`. Poll for the actual outcome, which can race with completion. A gateway shutdown can drain the run or interrupt it. After losing the execution owner, keyed legacy status can report `interrupted` and the canonical admission path can report `unknown`. In the latter case, the affected session's queue waits for acknowledgement through `resolve-unknown` where advertised. Reconcile possible tool effects before acknowledging or starting the work again. Restart recovery is recovery of state, with no guarantee that the interrupted execution resumes. [Stop][stop] · [Restart status][status] · [Unknown resolution][unknown] · [Durable status source][durable] · [Stop race test][stop-test]
- If the turn delegates to a detached subagent, its late result belongs to session history and can arrive after the parent run settles. It does not reopen the parent stream. An explicit API session with server-side history allows the next turn to read that result. Check history again if Onyx needs to show detached completions. [Detached results][detached]

## Live checks before relying on the flow

1. On the intended Hermes version and profile, submit a slow, harmless tool-backed turn from device A. Close it after HTTP 202. Open Onyx on device B with no local state from A. Recover the same run ID, terminal status, final text, and persisted messages. Submit a follow-up that refers to the earlier answer.
2. Drop the HTTP 202 reply after admission. Retry the same body and key from the backend while the work is active and again after completion. Verify one execution and one transcript turn. Change the body under the original key and verify conflict. Confirm that signed-out devices cannot recover the record.
3. Disconnect and resume progress with the last sequence. Repeat after the stream buffer expires and verify polling still works. Come back after the intended retention interval and verify Onyx can still show the saved result. Exercise transcript paging and context compaction if needed for that interval.
4. Stop a run during a harmless tool call. Verify the difference between requesting stop and the final outcome. Test a graceful restart, a lost gateway process, and restoration after a completed run. Record which terminal or unknown states the deployed configuration returns and whether follow-ups are blocked.
5. If the first release allows concurrent submissions or approval prompts, submit from both devices to the same session and verify transcript order and cross-device approval recovery. If it allows detached subagents, verify a late result appears in history after the parent settles.
